hotswap · design

the swap moment for the gigantic primitives

Zero-downtime upgrades—hotswap moves a running tool to its next release and back, from inside the tool. mise and packslip release, verify, install and keep versions side by side; hotswap owns the moment between: drain, swap, smoke, then settle or roll back. One crate inside each tool, no daemon, no download code.

Why

The gigantic tools — grove, sandman, stele, routines, voice, bifrost, … — are independent primitives. bifrost, the desktop app, plugs them into one UI the way mise plugs in runtimes: install one and its UI appears — a routines tab, sandman's report page. A remote Mac runs the night shift and needs the releases the dev box gets.

jdx tooling first. packslip — "a vendor-neutral signed release manifest" — and mise's packslip: backend cover release, discovery, verification, install, upgrade and side-by-side versions. What they leave is the swap on a host where the tool is running: hotswap.

Release

Every tool's contract; hotswap relies on it, never owns it.

  • a GitHub Release per merge to main — trunk is the latest release, so every host follows one line.
  • versions are YYYY.M.N — mise's calendar form, N the count of the month's earlier v* tags, so a month opens at .0 (2026.11.0). packslip requires semver; four-part dates do not parse.
  • the release job builds <bin>-<target>.tar.gz for aarch64-apple-darwin (routines adds x86_64-unknown-linux-gnu for its CI tick), then runs jdx/packslip@v1 with artifacts, bin, tag and version: it attests the archives and signs packslip.sigstore.json with the workflow identity.
  • private repos — mise's packslip backend fetches private assets through the gh token (unverified 2026-11-01 · no private tool releases on packslip yet).
  • a signed release list — .well-known/packslip.json may recommend or withdraw a version.
permissions:
  attestations: write   # packslip attests each archive
  contents: write       # upload release assets
  id-token: write       # keyless sigstore, the workflow identity

The two-job form builds and uploads in one job and keeps the packslip job at contents: read.

Install and upgrade

mise does the package work; the tool's upgrade verb — this crate, linked in — does the swap. Nobody installs hotswap.

commandwhat it does
mise use -g packslip:jgeschwendt/<tool>
<tool> setup		install — publisher verification, signer continuity (packslip/pins.toml in mise's state dir), artifact digest, then the tool's install duties, its upgrade agent among them
<tool> upgrademise upgrade --bump <mise key>, then the swap; nothing new reads <tool> <v>: up to date, exit 0; a failed bump reads <tool>: mise upgrade failed: <mise's reason>, exit 1, nothing swapped
<tool> upgrade --backrollback through mise use -g <mise key>@<previous>, reachable until mise prunes the upgraded-from version after upgrade.prune_after (24 h default); an upgrade's own rollback runs in-process, unaffected
<tool> setup --remove
mise unuse -g <mise key>		uninstall — agents booted out and the record forgotten, then the pin
  • no release-age hold — mise hides a release from latest for 24 h by default, which would hide it from the upgrade tick and bifrost's rows; the global minimum_release_age_excludes lists each tool's full backend ID (packslip:jgeschwendt/sandman, …; a path glob such as packslip:jgeschwendt/* matches nothing, verified 2026-10-31), carried by the profile repo's ~/.config/mise/config.toml.
  • discovery lag — mise resolves releases through mise-versions.jdx.dev (s-maxage=600) and its own HTTP cache, so a release can take ten minutes to appear; mise cache clear drops the local copy.
  • the upgrade agent — dev.gigantic.<tool>.upgrade, rendered by hotswap::agent_plist(tool, bin) and bootstrapped by <tool> setup: every 900 s (StartInterval), never at load (a load-time upgrade would race the swap that ran setup), logging to ~/Library/Logs/<label>.log. It runs <mise data dir>/shims/<bin> upgrade; a shim re-resolves the global version on every exec, so the agent follows the active version and survives its own swap, which never kickstarts it. upgrade hands every step a PATH led by the shims, so each step runs the version mise just made active.
  • other bumps — a daily mise upgrade --bump may move a tool first; the next tick swaps to it, since upgrade acts on any active version its record does not hold.

Mechanism

One function, hotswap::upgrade, inside the tool. It finds the tool's mise key (the backend key ending in the tool's name) and active version in mise ls --json, run from / so no project pin hides the global one, and acts when that version differs from its record's; a red record stays put until a new version or --back. It speaks mise only for ls --json, latest, upgrade --bump and use -g.

<tool> upgrade           # mise upgrade --bump, then drain, swap, smoke, settle or roll back
<tool> upgrade --check   # report what would happen; touch nothing
<tool> upgrade --back    # a deliberate rollback to the previous version
<tool> upgrade --retry   # a plain upgrade past the red hold
  1. Drain — run the manifest's drain commands (§ contract); a refusal aborts: nothing swapped, nothing rolled back. A running process keeps its binary — mise installs by unlink and create — so only new processes see the new version.
  2. Swap — <tool> setup, then launchctl kickstart -k each manifest agent except the tool's upgrade agent, whose kick would kill the running swap; setup first, since it bootstraps an agent a release adds and kickstarting an unloaded label fails.
  3. Smoke — the manifest's smoke commands, against the new processes.
  4. Settle or roll back — green: record the swap in ~/.local/state/hotswap/<tool>.json. Red: record the version red, so a crash from here on reads red; mise use -g <mise key>@<previous>, then setup, kickstart and smoke under the same manifest; exit 1 naming the failing probe. A previous version mise no longer holds, or whose record is red, is never rolled back onto unless it held (passed its own steps as a rollback target); the failed version then stays current, red.
  • the red hold — the record's red names the version a run failed on, rolled back from, or left by --back. Before bumping, upgrade asks mise latest <key>; while latest is that version it prints <tool>: <v> is red; waiting for a newer release and exits 1 without touching mise (--check shows it, exit 0). A newer release or a failed mise latest goes through, a green swap clears it, --retry passes it. Without it the agent's --bump would move a rollback's pin back onto the red release every tick.
  • the manifest is the running binary's — the upgrading version supplies agents, drain and smoke for the new version and the rollback; setup, run through the shim, is the new version's.
  • the record — the last swap: at, ok, smoke output, version and previous; a rollback's names the failing probe (and the rollback's own, if red too), keeps previous off the failed version, names it in red, and sets held when the rolled-back-onto version passed its steps. A lock beside it keeps two upgrades of one tool apart.
  • no version directory, no daemon — mise downloads, verifies and stores versions; the upgrade agent, a person or bifrost decides when to call.

The tool contract

Two verbs, owned by the tool; hotswap is a git dependency, hotswap = { git = "https://github.com/jgeschwendt/hotswap" }.

  • <tool> setup [--remove] — the idempotent install duties, run by bifrost's install and after every swap: render the launchd templates (carrying {{HOME}}) and bootstrap the agents, the upgrade agent from hotswap::agent_plist among them; install routine docs into ~/.routines, leaving an edited copy alone; register MCP servers; print what it did. --remove inverts it and calls hotswap::forget(tool) so a reinstall starts clean; the tool's data stays.
  • <tool> upgrade [--check | --back | --retry] — hotswap::upgrade(tool, &manifest, &args), its return the exit code: 0 green or settled, 1 red, 2 unable to try.
  • three names, one identity — the tool name is the mise key's last segment (packslip:jgeschwendt/routines), the label stem (dev.gigantic.routines.*) and the record (~/.local/state/hotswap/routines.json). bin names the executable when it differs — routines ships routine and renders agent_plist("routines", "routine"); empty, the tool name stands in.
  • the shims dir — hotswap::shims(): MISE_DATA_DIR, else XDG_DATA_HOME/mise, else ~/.local/share/mise, then shims — the plist's lookup, for a setup that links ~/.local/bin/<bin> to <shims>/<bin>.

The manifest, in code

Every field may be empty; ..Default::default() swaps with nothing to run.

let m = hotswap::Manifest {
    agents: vec!["dev.gigantic.sandman.report".into()],  // kickstarted on swap
    setup: vec!["sandman".into(), "setup".into()],       // run after every swap
    smoke: vec![vec!["sandman".into(), "version".into()], vec!["sandman".into(), "shift".into(), "status".into()]],
    timeout: Some(120),  // seconds per step, the default; expiry kills the step's process group
    ..Default::default() // no drain: a shift keeps the binary it started on
};
std::process::exit(hotswap::upgrade("sandman", &m, &args));

A step that exits while a background child holds its output is waited out to the deadline, then judged by its own exit code — detach daemons from stdout.

The runtime layer is a mise pin only if mise's erlang installs the prebuilt otp_builds on macOS (unverified 2026-11-01 · not yet probed).

Non-goals

  • A daemon — callers decide when to swap.
  • Download or signature code of its own — mise and packslip.
  • A package manager — that is mise.
  • A release format — that is packslip.
  • Signing beyond packslip's keyless sigstore, until the owner says otherwise.
  • Third-party tools — the gigantic primitives only.
  • A version directory of its own — mise keeps versions side by side.
