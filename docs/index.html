hotswap · design

the swap moment for the gigantic primitives

Zero-downtime upgrades—hotswap moves a running tool to its next release and back, from inside the tool. mise and packslip release, verify, install and keep versions side by side; hotswap owns only the moment between: drain, swap, smoke, then settle or roll back. One crate inside each tool, no daemon, no download code.

Why

The gigantic tools — grove, sandman, stele, routines, voice, bifrost, … — are independent primitives; each is used however suits whoever picks it up. bifrost, the desktop app, plugs them into one UI the way mise plugs in runtimes: an optional install, and once installed the component's UI appears — a routines tab, sandman's report page. A remote Mac mini or studio runs the night shift and is worked on remotely; it needs the same releases the dev box gets.

jdx tooling first: one maintainer across the toolchain (mise, hk, mbx) is worth more than a marginal feature. packslip — crate 1.11.0, "a vendor-neutral signed release manifest" — and mise's packslip: backend already cover release, discovery, verification, install, upgrade and side-by-side versions. What they leave over is the moment of the swap on a host where the tool is running. That is hotswap.

Supersedes the shared-updater plan: grove's crates/grove/src/update/ — versions dir, current/previous links, pending-flip marker, canary walk, sha256 sidecar — duplicates mise and packslip and retires once grove adopts them. bifrost's selfupdate.rs and layer updater likewise.

Release

What every tool does — the contract hotswap relies on but does not own.

  • a GitHub Release per merge to main — trunk equals latest release, so the dev box and the remote Mac follow the same line.
  • versions are YYYY.M.N — mise's own calendar form, N counting the month's releases (2026.10.3). packslip requires semver; four-part dates do not parse.
  • the tag job builds <tool>-<target>.tar.gz per target (aarch64-apple-darwin first), uploads them, then runs jdx/packslip@v1 with artifacts: and bin: — it attests the files and signs packslip.sigstore.json with the workflow identity.
  • public and private alike — public repos release from their own CI; private ones (bifrost, voice) the same way, since mise's packslip backend fetches private assets through the gh token. The public *-releases mirror bifrost uses today retires.
  • a signed release list — a repo may publish .well-known/packslip.json to recommend or withdraw a version.
permissions:
  attestations: write   # packslip attests each archive
  contents: write       # upload release assets
  id-token: write       # keyless sigstore, the workflow identity

The safer two-job form builds and uploads in one job and keeps the packslip job at contents: read. Each tool's first release is the owner's call under his release policy.

Install and upgrade

mise does the package work; each tool's own upgrade verb — this crate, linked in — does the swap. Nobody installs hotswap.

commandwhat it does
mise use -g packslip:jgeschwendt/<tool>
<tool> setup		install — publisher verification, signer continuity (packslip/pins.toml in mise's state dir) and artifact digest checks, then the tool's own install duties, its upgrade agent among them
<tool> upgrademise upgrade --bump <mise key>, then the swap; nothing new reads <tool> <v>: up to date, exit 0; a failed upgrade reads <tool>: mise upgrade failed: <mise's reason>, exit 1, nothing swapped
<tool> upgrade --backinstant rollback through mise use -g <mise key>@<previous> — versions sit side by side until mise prunes the upgraded-from one after upgrade.prune_after (24 h default), so a later --back reaches it only inside that window; an upgrade's own rollback runs in the same process, unaffected
<tool> setup --remove
mise unuse -g <mise key>		uninstall — the agents booted out and the record forgotten first, then the pin
  • no release-age hold — mise's default holds latest 24 h, which would hide every release from the upgrade tick and from bifrost's rows; the machine's global mise settings list each tool's full backend ID in minimum_release_age_excludes (packslip:jgeschwendt/sandman and so on: a path glob such as packslip:jgeschwendt/* matches nothing, verified 2026-10-31). The list rides the profile repo's ~/.config/mise/config.toml, so a new machine carries it.
  • the upgrade agent — dev.gigantic.<tool>.upgrade, whose plist hotswap::agent_plist(tool, bin) renders and <tool> setup bootstraps: every 900 s (StartInterval), not at load (RunAtLoad false: a load-time upgrade would race the swap that ran setup), as a background process logging to ~/Library/Logs/<label>.log. It runs mise's shim <mise data dir>/shims/<bin> upgrade with the shims first on PATH; a shim re-resolves the global version on every exec, so the agent follows whichever version is active and survives its own swap, which never kickstarts it. A shim puts the running install's bin dir ahead of the shims, so upgrade hands every step a PATH led by the shims again: each step runs the version mise just made active.
  • the rest of the toolchain — whatever already bumps it on the host (a daily mise upgrade) keeps doing so, unchanged.

Mechanism

One function, hotswap::upgrade, inside the tool. It finds the tool's mise key (any backend whose key ends in the tool's name) and active version in mise ls --json, run from / so only the global config is active and no project pin hides it, and acts when that version differs from the one its record holds; a red record stays put until a new version or --back. mise is spoken only for ls --json, latest, upgrade --bump and use -g.

<tool> upgrade           # mise upgrade --bump, then drain, swap, smoke, settle or roll back
<tool> upgrade --check   # report what would happen; touch nothing
<tool> upgrade --back    # a deliberate rollback to the previous version
<tool> upgrade --retry   # a plain upgrade past the red hold
  1. Drain — ask the tool to finish or hand over what it holds, by the tool's own contract: grove's server drain ladder; a sandman shift keeps the binary it started on (install replaces by unlink and create, so a running process is untouched and only new processes see the new version); launchd agents are the swap point. A refused drain aborts: nothing swapped, nothing rolled back.
  2. Swap — run <tool> setup, then launchctl kickstart -k each agent the manifest declares (dev.gigantic.<project>[.<job>]) except the tool's own upgrade agent, whose kick would kill the running swap; setup first, since it bootstraps an agent a release adds and kickstarting an unloaded label fails.
  3. Smoke — run the manifest's smoke commands against the new processes.
  4. Settle or roll back — green: record the swap in ~/.local/state/hotswap/<tool>.json. Red: record the failed version red, so a crash from here on reads red, never green; mise use -g <mise key>@<previous>, then setup, kickstart and smoke under the same manifest, exit 1 naming the failing probe, and leave the record saying why. A previous version mise no longer holds installed, or whose record is red, is never rolled back onto, unless it held: passed its own steps as a rollback target. The failed version stays current, red.
toolsmoke
grovegrove --version · GET /api/health (curl, retried while the server boots after its grove off drain)
routinesroutine status
sandmansandman version · sandman shift status (a report-page probe would move its read cursor)
  • the red hold — the record's red names the version a run failed on, rolled back from, or left by --back. Before bumping, upgrade asks mise latest <key>; while latest is that version it prints <tool>: <v> is red; waiting for a newer release and exits 1 without touching mise (--check shows it, exit 0). A newer release, or a failed mise latest, goes through; a green swap clears it; --retry is the owner's explicit retry past it. Without it the 900 s agent's --bump would move a rollback's exact pin back onto the red release and swap to it again every tick.
  • the manifest is the running binary's — the version doing the upgrade supplies the agents, drain and smoke for both the new version and the rollback; setup, run through the shim, is the new version's own.
  • the record — the last swap only: version, previous, time, smoke output; a rollback's record names the probe that failed, and the rollback's own if it went red too, keeps previous off the version that failed, names that version in red, and marks held when the rolled-back-onto version passed its own steps. A lock beside it keeps two upgrades of one tool apart.
  • never a version directory — hotswap never downloads, verifies or writes one; mise did.
  • no daemon — the tool's upgrade agent, a person or bifrost decides when to call it.

The tool contract

What every tool owns: two verbs. The duties live with the tool; hotswap is a git dependency, hotswap = { git = "https://github.com/jgeschwendt/hotswap" }.

  • <tool> setup [--remove] — one idempotent verb for the install duties, run by bifrost's install and after every swap: render the launchd templates (carrying {{HOME}}, as sandman's plist already does) and bootstrap the agents, the upgrade agent from hotswap::agent_plist among them; install routine docs into ~/.routines where the tool ships them, leaving an edited copy alone; register MCP servers; print what it did. --remove is the inverse: agents booted out, routine docs and MCP registrations removed, hotswap::forget(tool) to drop the record and lock so a reinstall starts clean, the tool's data left alone.
  • <tool> upgrade [--check | --back | --retry] — hotswap::upgrade(tool, &manifest, &args), its return the exit code: 0 green or settled, 1 red, 2 unable to try. Every tool gains it with its first packslip release; none has one yet.
  • three names, one identity — the tool name is the mise key's last segment (packslip:jgeschwendt/routines), the label stem (dev.gigantic.routines.*) and the record (~/.local/state/hotswap/routines.json). The executable may differ: routines ships routine, so its manifest sets bin: "routine".into(), which names the usage line, and its setup renders agent_plist("routines", "routine"); empty, the tool name stands in.
  • the shims dir — hotswap::shims(), mise's MISE_DATA_DIR, else XDG_DATA_HOME/mise, else ~/.local/share/mise, then shims: the lookup the plist uses, for a setup that links ~/.local/bin/<bin> to <shims>/<bin>, as sandman's does.

The manifest, in code

Every field may be empty; ..Default::default() swaps with nothing to run.

let m = hotswap::Manifest {
    agents: vec!["dev.gigantic.sandman.report".into(), "dev.gigantic.sandman.upgrade".into()],  // kickstarted on swap, the upgrade agent skipped
    setup: vec!["sandman".into(), "setup".into()],                                           // run after every swap
    smoke: vec![vec!["sandman".into(), "version".into()], vec!["sandman".into(), "shift".into(), "status".into()]],
    timeout: Some(120),  // seconds per step, the default; expiry kills the step's process group
    ..Default::default() // drain: a shift keeps the binary it started on
};
std::process::exit(hotswap::upgrade("sandman", &m, &args));

A step that exits while a background child still holds its output is waited out to the deadline, then judged by its own exit code — detach daemons from stdout.

Non-goals

  • A daemon — callers decide when to swap.
  • Download or signature code of its own — mise and packslip.
  • A package manager — that is mise.
  • A release format — that is packslip.
  • Signing beyond packslip's keyless sigstore, until the owner says otherwise.
  • Third-party tools — the gigantic primitives only.
  • A version directory of its own — mise keeps versions side by side.
