hotswap · design

the swap moment for the gigantic primitives

Zero-downtime upgrades—hotswap moves a running tool to its next release and back. mise and packslip release, verify, install and keep versions side by side; hotswap owns only the moment between: drain, swap, smoke, then settle or roll back. One binary, no daemon, no download code.

Why

The gigantic tools — grove, sandman, stele, routines, voice, bifrost, … — are independent primitives; each is used however suits whoever picks it up. bifrost, the desktop app, plugs them into one UI the way mise plugs in runtimes: an optional install, and once installed the component's UI appears — a routines tab, sandman's report page. A remote Mac mini or studio runs the night shift and is worked on remotely; it needs the same releases the dev box gets.

jdx tooling first: one maintainer across the toolchain (mise, hk, mbx) is worth more than a marginal feature. packslip — crate 1.11.0, "a vendor-neutral signed release manifest" — and mise's packslip: backend already cover release, discovery, verification, install, upgrade and side-by-side versions. What they leave over is the moment of the swap on a host where the tool is running. That is hotswap.

Supersedes the shared-updater plan: grove's crates/grove/src/update/ — versions dir, current/previous links, pending-flip marker, canary walk, sha256 sidecar — duplicates mise and packslip and retires once grove adopts them. bifrost's selfupdate.rs and layer updater likewise.

Release

What every tool does — the contract hotswap relies on but does not own.

  • a GitHub Release per merge to main — trunk equals latest release, so the dev box and the remote Mac follow the same line.
  • versions are YYYY.M.N — mise's own calendar form, N counting the month's releases (2026.10.3). packslip requires semver; four-part dates do not parse.
  • the tag job builds <tool>-<target>.tar.gz per target (aarch64-apple-darwin first), uploads them, then runs jdx/packslip@v1 with artifacts: and bin: — it attests the files and signs packslip.sigstore.json with the workflow identity.
  • public and private alike — public repos release from their own CI; private ones (bifrost, voice) the same way, since mise's packslip backend fetches private assets through the gh token. The public *-releases mirror bifrost uses today retires.
  • a signed release list — a repo may publish .well-known/packslip.json to recommend or withdraw a version.
permissions:
  attestations: write   # packslip attests each archive
  contents: write       # upload release assets
  id-token: write       # keyless sigstore, the workflow identity

The safer two-job form builds and uploads in one job and keeps the packslip job at contents: read. Each tool's first release is the owner's call under his release policy.

Install and upgrade

mise does all of it; hotswap adds nothing here.

commandwhat it does
mise use -g packslip:jgeschwendt/<tool>install with publisher verification, signer continuity (packslip/pins.toml in mise's state dir) and artifact digest checks
mise upgrademove to the newest eligible version
mise use -g <tool>@<previous>instant rollback — versions sit side by side until mise prunes the upgraded-from one after upgrade.prune_after (24 h default), so a later --back reaches it only inside that window; the tick's own rollback runs in the same tick, unaffected
mise ls --jsonthe inventory
  • no release-age hold — our tools set the tool option minimum_release_age = "0s"; mise's default holds latest 24 h.
  • its own agent — dev.gigantic.hotswap, a launchd agent hotswap installs with hotswap setup, every 900 s (StartInterval) on each host and not at load (RunAtLoad false: a load-time tick would race the swap that ran setup): hotswap tick runs mise upgrade for the gigantic tools, then hotswap <tool> for each in its own process group, exiting 1 on a failed upgrade or any red swap. The plist runs mise's shim <mise data dir>/shims/hotswap tick with the shims first on PATH; a shim re-resolves the global version on every exec, so the agent follows whichever hotswap is active, survives hotswap swapping itself, and every step after the upgrade runs the new binaries; no swap ever kickstarts it. Tools are independent at runtime: nothing here requires routines, grove or sandman to run.
  • the rest of the toolchain — whatever already bumps it on the host (a daily mise upgrade) keeps doing so, unchanged.

Mechanism

One binary, installed like any other tool. It acts when a tool's current version (mise ls --json, run from / so only the global config is active and no project pin hides it) differs from the version its record holds; a red record stays put until a new version or --back.

hotswap <tool>           # drain, swap, smoke, settle or roll back
hotswap <tool> --check   # report what would happen; touch nothing
hotswap <tool> --back    # a deliberate rollback to the previous version
hotswap setup [--remove]  # install (or boot out) its own agent, idempotently
hotswap tick              # what the agent runs through its shim: mise upgrade, then a swap per tool; exit 1 on either red
  1. Drain — ask the tool to finish or hand over what it holds, by the tool's own contract: grove's server drain ladder; a sandman shift keeps the binary it started on (install replaces by unlink and create, so a running process is untouched and only new processes see the new version); launchd agents are the swap point. A refused drain aborts: nothing swapped, nothing rolled back.
  2. Swap — run <tool> setup, then launchctl kickstart -k each agent the tool declares (dev.gigantic.<project>[.<job>]); setup first, since it bootstraps an agent a release adds and kickstarting an unloaded label fails.
  3. Smoke — run the tool's declared smoke commands against the new processes.
  4. Settle or roll back — green: record the swap in ~/.local/state/hotswap/<tool>.json. Red: mise use -g <mise key>@<previous>, then setup, kickstart and smoke under the previous version's own hotswap.toml, exit 1 naming the failing probe, and leave the record saying why.
toolsmoke
grovegrove doctor --dry-run
routinesroutine status
sandmansandman version · sandman recall --cwd · sandman shift status
  • the record — the last swap only: version, previous, time, smoke output; a rollback's record names the probe that failed, and the rollback's own if it went red too, and keeps previous off the version that failed.
  • never a version directory — hotswap never downloads, verifies or writes one; mise did.
  • no daemon — its launchd agent, another agent or bifrost decides when to call it.

<tool> setup

What every tool owns: one idempotent verb for its install duties. hotswap calls it after a swap; a fresh host calls it once after mise install. The duties live with the tool, never in hotswap.

  • launchd — render its templates (carrying {{HOME}}, as sandman's plist already does) and bootstrap the agents.
  • routine docs — where the tool also ships orchestration for a host that runs routines, install them into ~/.routines, leaving an edited copy alone; the tool runs without them.
  • MCP — register its servers.
  • report — print what it did.
  • --remove — the inverse, for bifrost's uninstall toggle: boot the agents out, remove the routine docs it installed and its MCP registrations, leave the tool's data alone, print what it undid.

hotswap.toml

Shipped at the root of the release archive (the install path). Every field is optional; a tool without the file swaps with nothing to run.

agents = ["dev.gigantic.sandman.report"]          # kickstarted on swap
# drain = [...]                                   # optional; a shift keeps the binary it started on
setup  = ["sandman", "setup"]                     # run after every swap
smoke  = [["sandman", "version"], ["sandman", "shift", "status"]]
timeout = 120   # seconds per step; expiry kills the step's process group

A step that exits while a background child still holds its output is waited out to the deadline, then judged by its own exit code — detach daemons from stdout.

Non-goals

  • A daemon — callers decide when to swap.
  • Download or signature code of its own — mise and packslip.
  • A package manager — that is mise.
  • A release format — that is packslip.
  • Signing beyond packslip's keyless sigstore, until the owner says otherwise.
  • Third-party tools — the gigantic primitives only.
  • A version directory of its own — mise keeps versions side by side.
